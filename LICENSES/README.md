# LICENSES 目录说明

> 路径：
>
> ```text
> ~/.codex/skills/professional-screenwriter/LICENSES/
> ```
>
> 本目录用于管理：
>
> ```text
> 本 Skill 的许可；
> 第三方材料的版权、许可、署名与通知；
> 项目资产的授权范围、期限与使用边界；
> 与发布、分发、客户交付和生产相关的权利记录。
> ```
>
> 本目录不是故事开发目录、研究资料库或普通附件目录。
>
> 核心原则：
>
> ```text
> 没有清楚的权利链，
> 就不进入最终交付。
> ```

---

# 这个目录解决什么问题

影视、剧本、AI 生成与生产项目通常同时接触：

```text
- 原创文字、模板、剧本和项目文件；
- 第三方图片、视频、音乐、音效、字体、地图、图标、代码和模型；
- 真实人物、声音、肖像、品牌、地点、社交内容和数据；
- 外部文章、新闻、论文、数据库和事实来源；
- 客户、雇主、合作方、平台和供应商提供的受合同限制材料；
- AI 工具的输入、输出、平台条款和相似性风险。
```

这些对象的权利状态并不相同。

```text
“我能打开这个网页”
≠
“我能复制这张图片”。

“这个新闻支持一个事实”
≠
“我能使用新闻照片、采访视频或原文表达”。

“我买了一个素材包”
≠
“我获得所有平台、地域、期限、再分发和 AI 使用权”。

“内容由 AI 生成”
≠
“输入、输出、声音、肖像、商标和平台条款都没有风险”。

“项目是虚构作品”
≠
“无需处理版权、商标、肖像、隐私、合同、安全或发行限制”。
```

本目录的目标不是替代法律意见，而是建立可追溯记录，使团队能回答：

```text
项目使用了什么？
谁拥有或控制相关权利？
项目如何使用？
许可是否覆盖这种用途？
需要怎样署名、通知、保留文本或限制分发？
是否需要替换、授权、法务审查或上游同步？
```

# 目录结构

```text
LICENSES/
├── README.md
├── skill-license.md
├── third-party-notices.md
└── asset-rights-register.md
```

若项目包含可执行代码、插件、自动化、模型权重或可分发软件组件，可按需要增加：

```text
LICENSES/
├── code-license.md
├── model-notices.md
├── font-licenses/
├── music-licenses/
├── vendor-licenses/
└── agreements/
```

> 不要为“看起来完整”而创建空目录。
>
> 只有在确实存在相应材料、义务或授权证据时才添加。

# 文件职责

| 文件 | 唯一职责 | 不承担什么 |
|---|---|---|
| `skill-license.md` | 说明本 Skill 自身原创内容可如何复制、改编、分发和署名 | 不授予第三方素材、使用者项目或真实人物的权利 |
| `third-party-notices.md` | 记录第三方材料的版权、许可、署名、通知、分发和 AI 使用义务 | 不等于完整资产授权证明或外部事实来源日志 |
| `asset-rights-register.md` | 逐项记录项目实际使用的素材、授权证据、使用范围、期限、地域、平台与交付状态 | 不替代许可文本、合同或法务意见 |
| `code-license.md` | 若存在独立代码，说明项目原创代码的许可 | 不自动覆盖文档、模板、资产或第三方代码 |
| `model-notices.md` | 若分发或依赖模型/权重，记录模型许可、版本、用途和限制 | 不替代每个 AI 输出的审阅记录 |
| `vendor-licenses/` | 保存必须随包提供的第三方许可文本和 NOTICE | 不应混放项目故事、剧本或开发笔记 |
| `agreements/` | 保存或定位授权书、合同、邮件批准、购买凭证或工作订单 | 不应公开上传保密协议或私人信息 |

# 与其他目录的边界

## `LICENSES/` 与 `governance/`

```text
LICENSES/
= 是否有权使用、复制、改编、展示、分发或授权某项材料。

governance/
= 项目为什么需要某个事实、变更或决策；
当前项目使用哪个版本；
外部研究支持什么主张；
某项变化会影响哪些下游文件。
```

| 问题 | 应进入的位置 |
|---|---|
| “这个网页证明某项历史事实吗？” | `governance/source-links.md` |
| “这张网页里的照片能否放进片尾？” | `LICENSES/third-party-notices.md` + `asset-rights-register.md` |
| “授权到期，必须删除某首音乐，会影响哪些镜头？” | `governance/upstream-notices.md` |
| “当前正式项目基线使用哪份资产包？” | `governance/project-manifest.md` |
| “这个版本与上一版本有什么重要差异？” | `governance/change-log.md` |
| “本 Skill 的模板可否被商业改编？” | `LICENSES/skill-license.md` |

## `LICENSES/` 与 `references/`

```text
references/
= 创作、格式、审查、钩子、生产交接的方法论。

LICENSES/
= 使用这些方法时涉及的材料、软件、资产、人物和表达的权利边界。
```

不要将以下内容放入 `LICENSES/`：

```text
- Story Bible
- 长片/分集大纲
- 场景卡
- 剧本
- 对白重写稿
- 审查报告
- 来源研究笔记
- 上游变更通知
- 生产分镜
- 普通素材文件
- 未验证的网页收藏
```

# 使用流程

## 1. 发现材料时

当你考虑使用任何外部材料，先不要立刻下载、复制、剪进成片、
放入 Prompt 或写入剧本。

先问：

```text
这是什么？

- 事实来源？
- 抽象灵感？
- 可识别的文本、图像、声音、字体、品牌、人物、软件、数据或模型？
- 客户/雇主/合作方提供的材料？
- AI 输入或输出？
```

然后按下列规则路由：

| 情况 | 记录位置 | 默认行动 |
|---|---|---|
| 仅核验外部事实，不复制表达 | `governance/source-links.md` | 记录 Claim、Source、限制与复核 |
| 仅获得抽象灵感，不复制具体表达 | 项目开发笔记；必要时内部说明 | 重建原创角色、情节、视觉和台词 |
| 计划复制、展示、改编、嵌入或分发第三方材料 | `third-party-notices.md` | 建立 `TP ID`，确认许可与使用范围 |
| 已确定纳入项目交付物的资产 | `asset-rights-register.md` | 建立资产记录、关联授权证据与使用位置 |
| 权利状态改变并影响故事、镜头、资产或发布 | `upstream-notices.md` | 创建通知并同步下游 |
| 项目已形成稳定新基线 | `change-log.md` | 汇总重大已确认变化 |

## 2. 使用前审查

每一项拟使用第三方材料至少要回答：

```text
材料是什么？
它来自哪里？
谁是已知权利人？
当前版本是什么？
项目具体使用什么部分？
是否会复制、裁切、翻译、改编、重绘、配乐、变声、训练、
嵌入、公开展示、商业发行或再分发？
项目将在哪些平台、地域、期限和媒体中使用？
是否需要署名、许可文本、NOTICE、链接、修改说明或源码？
是否存在肖像、声音、商标、隐私、地点、数据或合同等独立权利层？
是否可用原创或已授权替代品实现同一功能？
```

## 3. 纳入交付物前

在任何材料进入下列任一内容前：

```text
- 剧本 PDF、Pitch Deck、分镜、概念图、海报、预告片；
- 成片、剪辑、片尾、字幕、UI、音乐、音效、配音；
- AI 训练、微调、参考图、角色锚点、声音样本；
- 客户交付、平台上传、公开展示、广告、付费内容；
- 可下载的项目包、插件、模板、代码、模型或资产包。
```

必须：

```text
1. 在 third-party-notices.md 创建或更新 TP ID；
2. 在 asset-rights-register.md 创建资产级记录；
3. 保存许可、合同、发票、授权、条款版本或其他可定位证据；
4. 核验用途、地域、期限、平台、商业模式与修改权；
5. 处理署名、NOTICE、许可文本、片尾或 UI 义务；
6. 评估是否需要法务、顾问、平台或客户批准；
7. 将 P0/P1 问题作为发布阻断项处理。
```

## 4. 权利状态变化时

发生以下任一情况时，不能只改 `LICENSES/` 文件：

```text
- 授权到期或授权范围缩小；
- 第三方提出异议；
- 素材、音乐、品牌、台词、地图、字体、声音或 AI 输出必须替换；
- 项目从内部使用变为商业发布；
- 发行平台、地域、期限或商业模式扩大；
- 发现客户/员工/供应商材料存在合同限制；
- 发现原许可不覆盖当前用途。
```

必须执行：

```text
LICENSES 记录更新
→ governance/upstream-notices.md 影响分析
→ 更新剧本、镜头、资产、音频、字幕、UI、片尾和交付包
→ 运行权利与生产审查
→ governance/change-log.md 记录稳定版本变化
→ project-manifest.md 更新有效基线
```

# 许可层级与优先级

当多个权利文件同时存在时，按以下顺序检查：

```text
1. 适用法律、法院命令、监管要求与不可放弃权利；
2. 已签署的客户、雇佣、授权、保密、演出、地点或供应商合同；
3. 第三方材料的专门许可证、NOTICE、平台条款和权利人限制；
4. 项目级资产授权与使用范围；
5. 本 Skill 的原创内容许可；
6. 项目内部说明、README、工作流偏好与创作习惯。
```

重要规则：

```text
更通用的文件不能覆盖更具体的限制。

例如：
- CC BY 4.0 的 Skill 模板许可，
  不会覆盖用户贴入模板的一张第三方图片；

- 项目内部“可商用”标记，
  不会覆盖素材供应商“仅个人使用”的条款；

- 已购买字体，
  不会自动允许把字体文件嵌入并再分发给客户；

- AI 平台允许生成，
  不会自动处理输入图片、真实人物声音或输出相似性的风险。
```

# 最小文件标准

## 使用本 Skill 时

最低应维护：

```text
LICENSES/
├── README.md
├── skill-license.md
└── third-party-notices.md
```

若项目没有使用任何第三方材料：

```text
third-party-notices.md
```

仍应保留，并明确写明：

```text
当前未发现或未纳入需要第三方许可、署名或通知处理的材料。

本结论仅适用于当前项目版本与已登记交付物；
未来使用图像、音乐、字体、代码、地图、品牌、人物、
声音、AI 工具、模型、数据或外部资产时，必须重新评估。
```

## 进入生产或公开发布时

至少还应维护：

```text
LICENSES/
├── asset-rights-register.md
├── third-party-notices.md
├── [[必要的许可证原文或 NOTICE]]
└── [[授权书/购买凭证/许可证明的安全存储路径]]
```

如果项目包含代码、插件、模型、字体、素材包或可下载资产：

```text
- 保存每个直接分发组件的适用许可与版权信息；
- 保存许可要求的 NOTICE、署名或完整许可文本；
- 检查是否存在源代码、同许可、修改说明或再分发义务；
- 不将第三方代码或材料错误声明为项目原创；
- 不让资产归档路径泄露客户机密、私人信息或受限合同内容。
```

直接分发第三方组件通常需要保留相应版权与许可信息；某些许可还可能要求额外的通知、源码提供或其他义务，因此应以具体许可文本和专业审阅为准。

# 常见误区

| 误区 | 为什么错误 | 正确动作 |
|---|---|---|
| “网上有，所以能用” | 公开访问不等于获得复制或商业使用权 | 找到许可、授权或使用原创替代 |
| “只用几秒/几句话” | 数量不是唯一判断标准；可识别性和使用方式仍重要 | 不假定例外；记录并审查 |
| “我改了很多，所以是原创” | 改编仍可能涉及原作表达和衍生权 | 只提取抽象机制，重建原创表达 |
| “只用于内部 Pitch” | 内部、客户、投资人或合作方使用仍可能受合同和权利限制 | 确认用途、对象与保密边界 |
| “买过素材，所以什么都能用” | 许可常限制平台、地域、期限、嵌入、再分发、AI 和商业用途 | 阅读购买时对应的完整条款 |
| “Creative Commons 就等于免费” | 不同 CC 条款对商业、改编、同许可和署名要求不同 | 核验具体版本与项目兼容性 |
| “公版就没有任何风险” | 版本、译本、录音、摄影、商标、人格和地域可能另有权利 | 核验具体材料与发行地 |
| “AI 生成的，不会侵权” | 输入、输出、人物、声音、平台条款与相似性都可能有风险 | 记录 AI 工具、输入、输出和审阅 |
| “改了名字就不涉及真实人物” | 仍可能可识别，且问题不只在名称 | 评估整体识别性、情节和商业用途 |
| “LICENSES 是法律团队的事” | 创作、资产、制作和发布阶段都需要早期发现风险 | 发现即登记，必要时升级审阅 |
| “先上线，出问题再删” | 可能造成侵权、违约、下架、重做和声誉损失 | 未清权不进入最终交付 |

# 对抗式审查

更新本目录或准备发布前，执行以下问题。

## 权利链检察官

- 这项材料是否真的由我们拥有，或已获得足够授权？
- 我们是否知道材料的具体版本、来源、权利人和许可文本？
- 是否只确认了版权，却遗漏表演、录音、肖像、商标、隐私、地点、字体、数据或合同层？
- 是否把截图、转发、下载、购买、平台可见性或口头同意误认为完整权利？
- 授权范围是否覆盖当前平台、地域、期限、受众、商业模式和修改方式？

## 使用方式检察官

- 项目具体复制或展示了什么？
- 是否从内部参考悄悄升级为公开、广告、付费、客户交付或可下载分发？
- 是否进行了裁切、翻译、改编、重绘、重录、变声、训练、微调或合成？
- 当前许可是否允许这些具体动作？
- 是否有原创替代方案能完成同样的故事或视觉功能？

## 署名与分发检察官

- 是否需要版权声明、署名、许可证链接、完整许可、NOTICE、修改说明或源码？
- 这些信息是否被放在正确的地方：片尾、字幕、About、README、下载包、UI 或元数据？
- 最终交付物是否遗漏了某个第三方字体、音乐、代码、图标、地图、模型或素材？
- 是否把项目原创许可错误应用到第三方材料？

## AI 检察官

- 输入是否含客户机密、个人资料、未授权文本、图片、声音或视频？
- 输出是否接近真实人物、演员、创作者、商标、角色或已知作品？
- 平台条款是否允许当前的商业、客户、地域和再分发用途？
- 是否保存了足够记录，以定位某个最终输出的模型、日期、输入来源和审阅结论？
- 是否误以为模型或平台的“可商用”声明覆盖了全部第三方风险？

## 发布检察官

- 是否存在任何 `P0`、`DISPUTED`、`EXPIRED`、`DO_NOT_USE` 或未处理 `P1` 项？
- 每个实际进入成片、剧本、Pitch、素材包或下载包的第三方对象是否有 `TP ID`？
- 片尾、字幕、项目说明、下载包、许可文件与登记册是否一致？
- 若收到权利异议，是否能在短时间内定位使用位置、授权证据、负责人和替代方案？
- 权利变更是否已同步到剧本、镜头、资产、声音、字幕、UI、生产包和项目版本？

# 发布前门禁

公开发布、客户交付、平台上传、广告投放、商业分发或可下载打包前，确认：

- [ ] 已盘点所有第三方文本、图片、视频、音乐、声音、字体、图标、地图、软件、模型、数据、品牌、人物和 AI 材料
- [ ] 每项实际使用的第三方材料均已在 `third-party-notices.md` 建立 `TP ID`
- [ ] 每项实际使用资产均已在 `asset-rights-register.md` 建立记录
- [ ] 授权、许可、购买凭证、合同、条款版本或权利证据可定位
- [ ] 使用方式、地域、期限、平台、商业模式、改编和再分发均在授权范围内
- [ ] 所有必要署名、NOTICE、许可文本、片尾、About、README、字幕或 UI 已加入
- [ ] 所有开源代码、字体、模型、插件和直接分发组件的许可义务已完成
- [ ] 所有 AI 输入与输出均已完成必要审阅
- [ ] 所有真实人物、声音、肖像、品牌、商标、地点和敏感数据均已处理
- [ ] 所有 `P0` 已关闭；任何 `P1` 例外均有书面批准、负责人、到期日和补偿措施
- [ ] 权利变更已通过 `upstream-notices.md` 同步至所有受影响下游文件
- [ ] `project-manifest.md`、`change-log.md`、生产包与最终交付物指向同一有效基线
- [ ] 必要时已获得法务、客户、平台、顾问、表演者、场地或供应商批准

# 最终原则

```text
LICENSES 目录不是一个在发布前才检查的附件夹。

它是创作、研究、资产、AI、制作和发行共同依赖的控制面。

它让团队在使用任何外部材料前先问：

我真的有权这样使用它吗？
```
