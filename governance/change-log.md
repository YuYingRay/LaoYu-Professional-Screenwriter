# 1. 第一性原理

## 1.1 变更日志的唯一问题

```text
相对于上一可用基线，
项目中哪些重要事实、结构、交付物、约束、风险或生产决策已经改变？
```

## 1.2 何为“值得记录的变更”

若一项修改会改变以下至少一项，通常必须进入变更日志：

- 项目格式、受众、时长、画幅、平台或商业模型
- Logline、核心问题、主题命题或类型承诺
- 主角目标、错误信念、主要对手、失败代价或高潮选择
- 世界规则、规则成本、时间线、关键道具、角色伤病或关系状态
- 信息揭示、谜团回收、集尾钩子、付费点或兑现窗口
- 结构、分集顺序、场景功能、结局、人物生死或身份
- 已锁定剧本、分镜、镜头、资产、配音、字幕、UI 或后期文件
- 预算、地点、角色、群演、动作、VFX、AI 生成策略或排期
- 权利、版权、肖像、品牌、隐私、安全、敏感内容或专业顾问要求
- 项目已知风险、接受风险、废弃策略或必须迁移的旧文件

以下内容一般不应单独进入变更日志：

```text
- 单句台词润色，且不改变信息、人物知识或场景结果；
- 拼写、格式、标点和命名统一；
- 未采用的 brainstorm；
- 尚未确认的搜索线索；
- 没有影响任何交付物的内部笔记；
- 没有改变事实、镜头功能或生产成本的措辞压缩。
```

若局部修改同时导致角色知道新信息、道具易主、伤病改变、场景目标改变或资产失效，它不再只是“台词润色”，必须记录。

## 1.3 不可替代的原则

```text
变更日志记录“已经发生的项目变化”，
而不是“希望发生的项目变化”。

上游通知回答“如何同步与验证”；
变更日志回答“最终到底改成了什么”。

若一项变更没有明确的前后差异、
没有对应版本、没有关联事实源、
没有关闭或接受风险的证据，
它不应进入正式版本条目。
```

# 2. 版本策略

> 不强制使用软件语义版本。
>
> 但所有项目必须有一个可解释、可比较、可回滚的版本命名方式。

## 2.1 推荐版本格式

```text
vMAJOR.MINOR.PATCH
```

示例：

```text
v0.1.0
v0.4.0
v0.4.3
v1.0.0
v1.1.0
v1.1.1
```

## 2.2 版本含义

| 级别 | 何时递增 | 示例 |
|---|---|---|
| `MAJOR` | 核心项目承诺、格式、故事发动机、主角/对手、高潮/结局、平台或制作模式发生破坏性改变 | 长片改竖屏短剧；主角目标重写；结局重构；实拍改 AI 主导 |
| `MINOR` | 新增完整模块、稳定的故事段落、分集、资产体系、生产交付物或显著但可管理的结构扩展 | 新增完整第二幕；加入付费点地图；新增生产交接包 |
| `PATCH` | 修复已知矛盾、连续性、事实、格式、局部场景或资产问题，且不改变核心承诺 | 修复道具归属；统一伤病；重写单场以恢复人物动机 |

## 2.3 开发阶段前缀

| 前缀 | 含义 | 示例 |
|---|---|---|
| `v0.x.x` | 探索与开发中，核心事实仍可能变化 | `v0.8.2` |
| `v1.0.0` | 首个完整、经审查、可供正式评估的基线 | `v1.0.0` |
| `v1.x.x` | 已进入稳定开发或剧本迭代 | `v1.3.1` |
| `LOCKED` | 某一交付物不应再随意修改 | `SCRIPT_LOCKED_v1.4.0` |
| `PROD` | 生产执行基线 | `PROD_v2.0.0` |
| `POST` | 后期执行基线 | `POST_v2.1.0` |
| `RELEASE` | 发布版本 | `RELEASE_v3.0.0` |

## 2.4 版本不是状态

```text
版本：
项目内容相对于基线发生了什么变化。

状态：
该版本是否正在草拟、审查、锁定、生产、废弃或发布。

示例：
v1.2.0 可以是 REVIEW；
v1.2.0 通过门禁后可以变为 LOCKED；
不是每次状态变化都必须创建新版本。
```

# 3. 条目分类

> 一项变更可同时属于多个类别。
>
> 例如“删除一个角色”可能同时是 `Removed`、`Changed`、`Production` 与 `Breaking`。

| 分类 | 用于记录 | 示例 |
|---|---|---|
| Added | 新增稳定交付物、故事模块、人物、规则、场景、资产或流程 | 新增第二幕维修船序列 |
| Changed | 已有事实、结构、策略、格式或制作方案改变 | 主角目标从自证改为救援 |
| Deprecated | 仍暂时可见，但不再应作为当前依据的文件、规则或资产 | 旧版角色资产卡待替换 |
| Removed | 已正式删除，不再是项目有效内容 | 删除“反派双胞胎”支线 |
| Fixed | 修复因果、连续性、格式、信息、生产或权利问题 | 修复角色在两地同时出现 |
| Security | 保密、访问、数据、账号、素材泄露或授权边界修复 | 删除未授权的私有参考素材 |
| Research | 外部事实、顾问结论、来源等级或研究限制改变 | 将医疗恢复规则降级为待顾问确认 |
| Production | 资产、预算、排期、镜头、AI、实拍或后期方案改变 | 复杂追逐改为声音与反应镜头 |
| Rights | 版权、肖像、商标、隐私、许可或法务决策改变 | 真实品牌替换为虚构品牌 |
| Risk | 已知风险、新增风险、风险接受或风险关闭 | 接受已拍镜头的服装差异，附补救字幕方案 |
| Breaking | 使旧下游文件、资产、引用或工作方式失效的变更 | 世界规则、人物身份、时间线或画幅改写 |

## 分类使用红线

```text
“Changed” 不应成为万能垃圾桶。

必须至少说明：
- 改了什么；
- 从什么改成什么；
- 对谁或什么产生影响；
- 是否为 Breaking；
- 关联哪个 upstream notice；
- 当前是否已验证。
```

# 9. 对抗式审查

## 9.1 变更日志检察官

- 这是一个可理解的项目变化，还是原始提交记录的复制？
- 读者只看此版本条目，能否理解项目从何处改到何处？
- 条目是否说明影响，而不是只说“优化”“调整”“加强”？
- 版本号是否与变更实际规模相称？
- 是否把结构重写伪装成 `PATCH`，以逃避下游同步？
- 是否存在重大变化未进入日志，只藏在某个文件里？
- 是否有已废弃内容仍被新的文件引用？

## 9.2 事实源检察官

- 变更日志是否与 Story Bible 的当前事实一致？
- 是否仍有旧角色身份、旧世界规则、旧时间线或旧道具状态散落在下游文件？
- 是否因更新剧本而忘记更新 Bible，或反过来？
- 当前有效基线表是否真的可用？
- 是否有多个文件同时宣称自己是最新版？
- 是否存在“最新版本在某人的记忆里”的隐性事实源？

## 9.3 因果检察官

- 本次 `Changed` 项是否改变人物选择？
- 若改变了选择，是否重审了前因与后果？
- 是否让中点、危机、高峰或结局失去支撑？
- 新增角色、秘密、规则或资产是否只增加复杂度而不产生因果？
- 被删除场景是否承载了未迁移的伏笔、关系变化或道具转移？
- 高潮是否仍来自主角选择，而不是临时资源、外援或巧合？

## 9.4 生产检察官

- 变更是否让已拍/已生成/已录音/已设计资产失效？
- 若资产未改，是否已明确接受何种连续性或叙事风险？
- 是否有视觉、口型、字幕、UI、镜头、画幅或道具后果未被记录？
- 是否把“预算下降”包装成创作选择，却没有验证故事仍成立？
- 是否因 AI/实拍限制改变故事，且该变化已向上游同步？

## 9.5 权利与安全检察官

- 变更是否引入真实人物、品牌、地点、声音、文本、图片或数据？
- 是否改变了版权、商标、肖像、隐私、敏感内容或平台风险？
- `source-links.md` 中的主张是否仍支持当前版本？
- 需要专业、法务或安全确认的事实是否被错误标记为已锁定？
- 是否存在因“虚构作品”而忽视现场安全、授权或发布风险的情况？

## 9.6 回滚检察官

- 如果此版本被否决，能否明确恢复到哪个基线？
- 哪些下游资产、字幕、音频、分镜或剧本需要一起回滚？
- 是否有无法回滚的制作动作？
- 是否已记录替代方案、接受风险与负责人？
- 当前版本是否把不可逆生产动作误报为普通修订？

# 11. 最终原则

```text
变更日志不是为了证明项目很忙。

它的价值是让任何协作者快速知道：

当前基线是什么；
这一版相对上一版哪里不同；
哪些旧文件、旧资产、旧规则已经失效；
哪些变化会破坏下游；
哪些风险已经修复、仍在开放或被明确接受；
以及在出现问题时应回滚到哪里。

如果变更日志无法帮助团队避免使用过期事实、
过期剧本、过期资产或过期研究结论，
它只是格式漂亮的历史噪声。
```
