# 1. 第一性原理

## 1.1 AI 视频不是一次性提示词任务

一个长镜头或连续剧的 AI 视频质量，不取决于提示词是否华丽，而取决于是否控制了以下变量：

```text
故事事实
+ 角色身份
+ 空间关系
+ 时间与状态
+ 镜头目的
+ 关键帧
+ 生成约束
+ 镜头间连续性
+ 选择与后期
```

如果没有这些变量，即使单条片段“很美”，也无法组成稳定剧情。

---

## 1.2 先锁故事，再拆镜头

禁止以下顺序：

```text
先生成很多漂亮视频
→ 再试图为片段补剧情
→ 发现角色、服装、空间、时间和情绪不连续
```

正确顺序：

```text
锁定剧本版本
→ 锁定人物与世界事实
→ 建立资产库
→ 分场拆解
→ 设计镜头叙事功能
→ 制作关键帧/分镜
→ 按批准路线生成单镜头或多镜头片段
→ 质检与挑选
→ 剪辑、声音、字幕、调色
→ 回写连续性与版本状态
```

---

## 1.3 生成的最小可控单元

先以 Shot 设计叙事，再以 Segment 组织一次生成；二者不能混同。单镜头路线的设计单元是：

```text
一个叙事目标明确的短镜头
+ 可见角色与资产
+ 可控动作
+ 明确起止状态
+ 连续性锚点
```

镜头长度应根据模型能力与动作复杂度选择。

以下用于单镜头设计与复杂度判断，不是禁止原生多镜头的全局限制：

- 单一动作优于连续多动作。
- 单一情绪变化优于复杂表演弧。
- 单一镜头目的优于“一个镜头讲完一场戏”。
- 起止状态明确优于只写抽象氛围。
- 可编辑的短片段优于不可控长片段。

已选原生多镜头路线时，保留逐镜目的、动作和接口，在同一次生成中完成有因果联系的覆盖。
不要因“一镜一个重点”退回单图固定机位，也不要把多个独立动作挤进没有切点设计的长镜头。

## 1.4 从完整剧本到成片的可复用闭环

观众获得的是信息、选择、情绪与后果，不是表格、图数或 Prompt 长度。用下表串联现有材料，
不为每一格新建文件或增加一次用户审批；执行边界仍按 §2.3 的有效委托。

| 环节 | 必须传到下一环的内容 | 验证方式 |
|---|---|---|
| 完整场景剧本 | 区分画面、角色对白、旁白、环境声与动作音效；人物为何说、听后如何变、选择造成什么后果 | 正文可读，不靠下游补写因果；见 §2.1、§7.5 |
| 导演编译与分段 | 必要信息 → 可见/可听证据 → 景别与机位 → 切点 → 相邻段起止状态 | 按导演参考的 Beat/Coverage/Edit/Shot/Segment 流程；镜数不替代可理解性 |
| 共用场域与逐镜净图 | 场地关系、角色身份及跨镜状态一致；定位、动作、情绪、细节各有需要的覆盖 | 检查整个实际输入组，而不只验一张漂亮母版；见 §6.5 |
| 模型执行包 | 完整 Prompt、逐图职责、说话人、原句与表演、动态环境、声音分工 | 反查批准剧本及真实上传文件；见 §7.2.1、§9 |
| 回片与整集剪辑 | 真实输出、实际声画、必要信息、相邻段接口和整体起伏 | 单段可剪不等于整集成立；正常速度连续观看，见 §11.3 |
| 用户反馈与复用 | 本版可接受之处、仍存问题、下一次应改变的决策及适用条件 | 按 §11.4 区分已观察事实、项目选择与待验证解释，不倒写旧证据 |

# 2. 生产前锁定

## 2.1 锁定门

在进入 AI 制作前，确认：

- [ ] 实际读取的 Skill 路径/版本与本次委托相符；候选试用不等于正式激活
- [ ] 当前完整场景剧本有明确版本，相关动作、对白、声音及前后场接口已同步到有效事实
- [ ] 场景、角色、道具和时间线已锁定
- [ ] 每场的叙事目标明确
- [ ] 每个主要角色有稳定视觉设定
- [ ] 关键关系、伤病、服装、道具状态已记录
- [ ] 内容权利、肖像、声音和音乐使用边界已确认
- [ ] 生成模型、分辨率、画幅、时长和输出格式已确定
- [ ] 制作预算、生成次数和人工修复能力已明确
- [ ] 已知模型限制已被标记
- [ ] 剧本中的高风险复杂动作已拆分或降级

若这些条件未满足，先输出“制作准备清单”，而不是直接生成数百条提示词。

源头检查须读相关正文，不能只认文件名、版本号、场景 ID 或旧批准。正文仍为历史稿、
待同步，或仅有大纲/场景卡时，先完成受影响场景剧本的修订与适用审查；不据下游卡片生成
正式生产 Prompt。用户明确授权的概念验证仍按 §16 限定范围，不要求为非剧情实验补整部剧本。

---

## 2.2 版本命名

所有生产文件必须共享统一版本名。

推荐规则：

```text
[[项目缩写]]_[[季/集]]_[[场次]]_[[镜号]]_[[版本]]_[[日期]]
```

示例：

```text
CITYLIGHTS_S01E01_SC03_SH012_v03_20260710
```

不要使用：

```text
final.mp4
final-final.mp4
really-final-new.mp4
last-one-2.mp4
```

推荐目录：

统一采用 `references/project-directory-structure.md` 的 `STRUCT-LAYERED`；
本手册的资产、预制作、生成与后期文件分别落入其中的 `assets/`、`production/`、
`script/exports/`与`archive/`职责目录。

## 2.3 有效委托与低打扰执行

先读取 Manifest 中当前有效、未被后续决定撤销的授权，核对其镜头/尝试、模型配置、资产与剧情锁、
预算及停止条件。历史“同意”、剩余预算或审查方建议不能单独扩大权限。
将依据、执行者、本次范围与例外写入现有导演卡或执行卡正文；不新增审批状态，也不改写合同的批准元数据语义。

- 委托已覆盖中间产物：自主完成序列卡、逐镜卡、Prompt、执行卡与适用审查，保持依赖顺序，不逐件再请示。
- 未被覆盖的生成、重试、路线/锁定事实变化或触发的停止条件：先明确缺少的决定，不把操作建议当授权。
- 区分委托人的批准依据、代理执行/自检与用户实际签字；不能把代理自审标成人工审查或虚构逐件批准。
- 用户保留最终作品裁决。已授权范围内提取不覆盖原片的本地临时证据属于审查步骤；仍遵守额外的明确限制。
- 实际提交均计入生成消耗，包括失败、无效或不可评样本；不规定所有项目统一的重抽数字。

# 3. 资产圣经

## 3.1 为什么资产先于镜头

角色、空间、道具和风格的一致性不能只靠每次重新写提示词。

需要将可复用事实外置为资产圣经：

```text
角色是谁
角色看起来怎样
角色此刻穿什么
角色与谁站在什么位置
场景具有哪些固定空间和光线特征
道具在何处、由谁持有、是否损坏
```

每次生成都从资产圣经引用，而不是重新发明。

---

## 3.3 角色参考图原则

角色参考图应尽量覆盖：

- 正面
- 45 度
- 左右侧面
- 全身比例
- 常用服装
- 关键表情
- 关键发型
- 特殊状态，例如伤痕、雨湿、工作服

如果工具支持，优先使用经过批准的角色参考图或角色卡，而非仅靠文本。使用同一角色的多角度参考图和稳定的视觉描述，有助于降低跨镜头漂移。

避免：

- 一张强滤镜、遮挡严重、极端表情的照片作为唯一角色参考；
- 用不同风格的多张图片混合做参考；
- 每集随意改变角色发型、服装主色、饰品位置；
- 在没有剧情解释时改变年龄、体型、五官或肤色。

## 3.4.1 环境动态与特殊状态

当环境运动或光效承担真实感、规则或情绪时，在现有场景卡与导演卡中区分：

| 层次 | 记录内容 |
|---|---|
| 固定空间 | 拓扑、对象身份、数量、尺度与主要光源；不要把保持场地误写成冻结水、植被或表情 |
| 持续动态 | 哪些水流、植被、颗粒或反射持续变化，以及本机位实际能看到什么 |
| 动作响应 | 起始状态 → 作用位置 → 局部介质响应 → 传播/衰减 → 次级响应；只写适用环节 |
| 特殊状态 | 谁拥有、功能与限制、建立/延续/消退条件、跨镜继承；机位裁切不等于状态消失 |

静态图锁定空间、材质、受光关系与动作起点；视频要求表达随时间发生的变化，不能用静态纹理冒充运动证据。
例如水幕应在相关镜头可见下落与落水响应；水下划动可扰动附近颗粒，不照搬露天浪花。
光斑、折射、发光与材质变化须有场景或已批准世界规则的依据；不要求每镜同时出现所有效果。
保护、投影等幻想规则先由项目设定决定，不能因制作方便新增能力、替人物解决冲突或改写现实行动。
必要状态若在上段缺失，下段须设计可理解的建立/变化，不通过改写历史接受记录掩盖接缝。

```text
城市灯光在人物面部形成可识别的冷暖对照。
```

# 4. 从剧本到场景拆解

## 4.1 先拆叙事，不先拆视觉

每个场景先回答：

```text
谁想要什么？
谁阻止？
权力如何变化？
观众必须在本场结束时知道或感到什么？
```

只有回答这些问题后，才决定镜头。

镜头不是“把剧本逐句拍出来”，而是用最少可控镜头传递场景中的行动、情绪、信息与转折。

---

## 4.2 场景拆解表

```md
| 场次 | 剧情版本 | 时长 | 地点 | 时间 | POV | 场景目标 | 对抗 | 转折 | 结束状态 | 关键资产 | 连续性风险 | 制作复杂度 |
```

示例：

```md
| S03 | v03 | 1m20s | 城市规划院会议室 | 夜 | 林夏 | 取得系统日志 | 周明阻止她导出 | 日志显示妹妹被标记 | 林夏决定私自入侵系统 | 林夏、周明、终端、停职通知 | 林夏右手擦伤；通知在桌上 | 中 |
```

---

## 4.3 场景到镜头的转换

每一个镜头都必须标注其主要叙事功能：

| 功能 | 镜头应回答的问题 |
|---|---|
| 定位 | 我们在哪里、何时、谁在场？ |
| 欲望 | 人物现在要做什么？ |
| 阻碍 | 什么或谁在阻止？ |
| 信息 | 观众需要知道什么？ |
| 反应 | 这一信息对人物意味着什么？ |
| 权力 | 谁暂时占上风？ |
| 转折 | 什么发生改变？ |
| 后果 | 人物接下来不得不做什么？ |

不要为了“镜头丰富”加入无叙事功能的空镜、慢推、转场或风景。

# 5. 镜头表

## 5.1 镜头表模板

需要设计景别、观看位置、物理摄影路径、转场触发与模型降级时，同时读取
`references/cinematography-director.md`；先完成 Camera Direction Card，再把批准字段回写镜头表。

多节拍、多镜头、跨场景或完整短片不得直接从 Scene Card 跳到镜头表或 Prompt。先完成并批准：

```text
Beat Map
→ Coverage Map
→ Edit Map
→ Shot Design
→ Segment Packing
→ Director Sequence Card
→ 逐镜 Camera Direction Card
→ 模型执行 Prompt
```

镜头表中的 `Segment` 表示一次模型提交产生的文件，不等于 `Shot`；一次 Segment 可以包含一个 Shot，
也可以包含有入口证据和关键切点验收的多 Shot 结构。多镜头空间关系须引用 Screen Direction Map，
持续镜头须引用 Timed Attention Path，承担 ESSENTIAL Beat 的镜头须写 Recovery Plan。

```md
| 镜号 | 场次 | 版本 | 时长 | 画幅 | 景别 | 机位/角度 | 运动 | 主体 | 动作 | 台词/声音 | 叙事功能 | 起始状态 | 结束状态 | 角色/场景/道具 ID | 连续性锚点 | 生成策略 | QC 状态 |
```

字段说明：

| 字段 | 要求 |
|---|---|
| 镜号 | 稳定唯一，例如 `S03_SH012` |
| 时长 | 只写必要长度，不追求单镜头过长 |
| 画幅 | `9:16`、`16:9`、`1:1` 等 |
| 景别 | ECU、CU、MCU、MS、MLS、WS 等 |
| 机位/角度 | 眼平、低机位、俯拍、侧后方等 |
| 运动 | 固定、轻推、平移、跟拍、手持等 |
| 主体 | 本镜必须被观众看见的重点 |
| 动作 | 一条主要可见动作 |
| 台词/声音 | 对白、环境声、音效、旁白 |
| 叙事功能 | 定位、欲望、阻碍、信息、反应、转折、后果 |
| 起始/结束状态 | 让镜头可控、可衔接 |
| 连续性锚点 | 服装、位置、手持物、视线方向、光线、伤病 |
| 生成策略 | 文生视频、图生视频、首尾帧、实拍混合、后期完成 |
| QC 状态 | 未生成、候选、待修、批准、弃用 |

---

## 5.2 镜头长度原则

不要为了模拟传统长镜头而把多个动作硬塞进一次生成。

经验规则：

| 镜头内容 | 建议策略 |
|---|---|
| 静态反应 | 短镜头，动作极少 |
| 单一手部动作 | 短镜头，重点控制道具和手 |
| 对话 | 设计说话与倾听覆盖；按批准路线在同段原生切换或分镜独立生成 |
| 走路进入空间 | 拆为建立镜头、进入镜头、反应镜头 |
| 激烈动作 | 拆成关键姿态、局部动作、后果镜头 |
| 信息揭示 | 特写 + 人物反应，避免一镜兼顾全部 |
| 大型事件 | 使用声音、闪光、反应、后果镜头拼接 |

单 Shot 的默认负荷为（多 Shot 的 Segment 按 §5.1 与导演参考的已批准路由打包）：

```text
一个主体
一个主要动作
一个明确空间
一个视觉重点
```

## 5.3 轴线与视线连续性

即使 AI 模型不真正理解电影语法，镜头表仍必须维护：

- 人物 A 位于画面左或右；
- 人物 B 对应位置稳定；
- 人物朝向稳定；
- 手机、门、窗、出口方向稳定；
- 角色进出方向一致；
- 重要道具在正确手中；
- 伤口、饰品和服装细节不跳变。

维护 `180 度轴线表`：

```md
| 场次 | 角色关系轴 | A 画面位置 | B 画面位置 | 主要视线方向 | 禁止反轴情况 |
```

如果故意反轴，必须有叙事理由，例如人物关系失衡、主观眩晕、危险突变；不能只是模型随机生成。

# 6. 关键帧与分镜

## 6.1 关键帧优先

对于需要连续性的镜头，优先顺序：

```text
批准的关键帧
→ 图生视频
→ 文生视频
```

原因：

- 关键帧能锁定人物、服装、空间、构图和情绪。
- 图生视频可将模型任务缩小为“让已有画面发生动作”。
- 文生视频更适合概念探索、空镜、非连续素材或无需严格一致性的镜头。

如果工具支持首尾帧，使用首帧锁定起点、尾帧锁定结局，尤其适合人物移动、转身、道具交接和状态变化。

## 6.2 分镜帧必须说明什么

每一张分镜帧至少表达：

```text
谁在画面中
角色处于何种状态
空间关系
镜头大小与角度
视觉重点
本镜的动作方向
与前后镜头的连续性
```

不要把“好看的概念图”误认为“可用的分镜帧”。

## 6.3 分镜审查

对每帧检查：

- 主体是否一眼可读？
- 人物姿态是否支持下一动作？
- 道具是否在正确位置？
- 角色朝向是否与前镜匹配？
- 是否有与剧本冲突的新服装、新物件、新人物？
- 是否有模型幻觉出的手指、文字、徽标、肢体或空间？
- 是否适合目标画幅，尤其是竖屏安全区？
- 该帧是否能自然衔接前后镜头？

## 6.4 输入约束的作用域检查

核对实际上传文件、顺序与职责，不只核对目录名或旧卡版本。把场景/角色卡、参考像素与 Prompt 联读：

| 限制 | 核查对象 | 合法例子 |
|---|---|---|
| 禁止引入某类对象 | 基准可为零，无需先登记一个被禁止对象 | 无人空景禁止新增人物 |
| 禁止复制既有对象 | 指代、数量和允许保留的原对象 | 保留水幕拱，禁止额外干拱 |
| 禁止改变身份或关系 | 同一对象的特征、位置、朝向或与其他对象关系 | 保留入口与逃生通道关系 |

不得因“拱门”等关键词同时出现在图片和禁令就判冲突；易混淆既有对象要正向命名。
明确标线、路缘等资产的真实含义，勿把齐平铺装误写成物理障碍。实际矛盾按导演参考 §2.6 的关键性处理。
登记表只有明确封闭列举时才表示“未列即不允许”；输出无新增物也可能因关系交换而不连续。
控制箭头/格栅与剧情内真实标线分开，不能把前者当资产，也不能因名称相似删除后者。

## 6.5 同场多图：场域与逐镜覆盖分开建立

- 先以已接受的场景母版固定影响剧情的地形、出入口、遮挡物和相对位置；再为本段实际机位补足空间。
  反向平视、斜俯视或正俯视可帮助对照，但不是每场必做的四视图，也不是可靠三维重建。
  母版未显示而剧情必用的区域应明确为美术补全，依项目决策权接受后成为共同设定；不能冒称从原图验证。
- 场域参考回答“同一个地方是什么”，逐镜净图回答“这一刻从哪里看、谁在做什么”。沿批准 Coverage
  制作所需的远、中、近、特写等构图，不用母版换文件名、纯裁切或多角度展示表冒充叙事分镜。
  裁切可用于已有信息的构图派生，但不能当作新增机位或新增证据。
- 分开记录空间不变量和随时间变化的状态。某物先受困后脱困、先被遮挡后可见，需要有动作依据；
  不是所有图一律静止相同，也不能把应在可见区域的物体擦除。不同时间的同一对象要标明起态/终态，
  不让两张参考暗示两个同时存在的对象。此说明仍需回片检验，不能保证模型不会复制。
- 成组核查实际上传文件：空间连接、身份/数量、前后状态、视线方向、透视尺度、接触遮挡、光照及 Prompt
  是否相容；微小纹理偏差不等同换场。已约定用户整组看图时，整组接受前不生成视频；替换图须重查受影响关系。
- 图数按叙事覆盖、实际入口容量、预算及本项目明确要求确定。用户已要求每段某个数量范围时须落实，
  不能用“最小充分”擅自减配；无此要求时不把一次有效的八图、十五秒或某组景别设成通用门槛。
  一图可约束身份或空间，多图可描述同一镜头的时间状态，故输入图数、Shot 数与生成次数分别记录。

# 7. 提示词架构

## 7.1 提示词的目标

镜头语言与运镜词不得从词库随机拼接。先按 `references/cinematography-director.md` 锁定叙事功能、
空间轴、一个主运动、起止状态和降级方案，再翻译为下方提示词结构。

采用 `NATIVE_MULTI_SHOT` 时，Prompt 包之前必须附当前平台入口的相近执行证据，或把任务明确标作 POC；
没有相近证据且要求确定性剪辑时，默认采用 `INDEPENDENT_SHOTS`。模型未执行 `DIRECTOR_CRITICAL`
切点且后期不可补救时，不得以 Prompt 格式正确代替成片失败。

提示词不是文学描写，而是对生成变量的最小充分约束。

高质量提示词应优先清楚描述：

```text
镜头
+ 可见主体
+ 单一动作
+ 空间
+ 光线/视觉条件
+ 连续性锚点
+ 约束
```

官方工具指南也通常建议把镜头类型、主体、动作、地点和视觉风格组合为清晰的视觉提示，而不是只给抽象评价词。

## 7.2 单镜头提示词模板

```md
[[画幅与镜头]]
[[角色身份与可见外观]]
[[单一动作]]
[[地点与空间关系]]
[[光线、时间与关键视觉条件]]
[[摄像机角度与运动]]
[[连续性锚点]]
[[风格与质量限制]]
[[负面约束]]
```

英文示例：

```text
Vertical 9:16 medium close-up, Lin Xia, a 32-year-old East Asian lighting designer
with a short black bob and a navy work shirt, stands at the left side of a dim city
planning office. She slowly lowers a red suspension notice onto a glass table.
Cold blue monitor light from camera right, warm sodium streetlight behind her,
shallow depth of field, locked eye-level camera, subtle handheld breath.
Her right hand has a small fresh scrape. The notice remains in her left hand
until the final second. No wardrobe change, no extra people, no text overlays,
no distorted hands, no sudden camera whip.
```

中文示例：

```text
竖屏 9:16，中近景，林夏，32 岁，短黑发，藏蓝色工作衬衫，
站在昏暗的城市规划院会议室画面左侧。她缓慢把红色停职通知放到玻璃桌上。
右侧显示器投下冷蓝光，身后窗外钠灯投下暖黄逆光，浅景深，眼平固定机位，
轻微手持呼吸感。林夏右手有新鲜擦伤。通知在镜头结束前始终由左手握住。
服装不变化，无额外人物，无屏幕文字，无畸形手指，无突兀甩镜。
```

不同模型对中文、英文、长短提示词和负面约束支持不同。必须针对实际模型测试，不要假设所有字段都生效。

## 7.2.1 原生多镜头完整 Prompt

适用于已按 §7.1 选择的多镜头路线。以下是独立重述的字段组织方法，不继承任何参考作品的情节、
台词或独特表达，也不宣称是平台规定语法。名称可适配当前入口；用户已认可的结构不要在下一包静默删减。

| 部分 | 应写清什么 |
|---|---|
| 全局 | 当前入口适用的时长、画幅、路线、音频模式；本段因果摘要与结尾尚未发生的事 |
| 风格 | 可见的造型、材质、动画与表演方式，不只写“电影级”；继承批准视觉体系 |
| 节奏 | 哪些信息迅速交代、哪里要看清证据、哪里完整说完或停顿；不将每图等时轮播 |
| 场景 | 同场地形、前中后景、遮挡与人物/关键物相对位置；哪些区域尚不可见 |
| 灯光与动态环境 | 光源及变化原因、与动作有关的水/风/粒子响应；特效建立、延续与消退，不静默增加能力 |
| 角色与声音 | 各角色身份、此段欲望与情绪变化、倾听反应；说话声音身份及原生对白/后期旁白/环境声/音效/音乐分工 |
| 逐图参考绑定 | 实际上传顺序与文件对应、图中内容、身份/空间/构图/时间状态职责、用于哪些镜头及不可推断的边界 |
| 镜头描述 | 按因果顺序写每镜景别、机位、表演、动作与证据、台词、声音触发、收尾和下一镜连接 |

逐镜写法示意，字段无关时省略；时间只是节奏建议，不保证逐秒执行：

```text
镜号｜参考时段｜图号（需对应实际文件）｜景别与机位
开镜继承什么 → 人物看到/做到什么 → 环境如何响应 → 怎样切向下一镜。
台词｜说话人（声音身份，画内/画外）：“该镜应说的完整原句。”
表演与声音｜说这句话想得到什么、语气与可演停顿、听者反应、音效发生在什么动作上。
收尾｜必须留下的状态或反应；哪些结果尚不能出现。
```

- 说话人、台词与对应镜头放在一起，不只在末尾列无归属的对白清单。除已写明的打断、重叠或画外音外，
  交接说话轮次，让听者反应可读；不能让镜外剪辑、角色标签或动作说明被当作台词念出。
- 完整语句、读证据和反应均占时长。容纳不下时，在批准范围内重分时或重分段；超范围提出取舍，
  不靠抢速、截句、删去交流或压掉必要镜头来满足固定秒数。
- 实际执行 Prompt 展开角色和图片职责，不能只交资产别名或“同上”。文件映射可随入口语法转写，
  未确认时不要假定多图都是首帧、都是硬关键帧，或模型支持某种引用标记。
- 区分导演预期与硬保证：图片只是输入约束；说话归属、时序、空间和关键切点必须看真实回片。
  修订与备用路线放在执行包，不把多个互斥方案同时交给模型任意选择。

## 7.3 提示词模块化

不要每次从零写完整提示词。

建立模块：

```text
CHAR_LIN_XIA
LOC_PLANNING_OFFICE_NIGHT
WARDROBE_LIN_WORK_01
PROP_SUSPENSION_NOTICE_01
STYLE_CITYLIGHTS_V01
CAM_MCU_EYELEVEL_LOCKED
ACTION_PLACE_NOTICE
NEG_HANDS_TEXT_EXTRA_PEOPLE
```

组合示例：

```text
CHAR_LIN_XIA + WARDROBE_LIN_WORK_01 + LOC_PLANNING_OFFICE_NIGHT
+ CAM_MCU_EYELEVEL_LOCKED + ACTION_PLACE_NOTICE
+ STYLE_CITYLIGHTS_V01 + NEG_HANDS_TEXT_EXTRA_PEOPLE
```

优点：

- 修改角色或场景时可批量更新；
- 避免同一角色被不同提示词描述成不同外观；
- 便于测试哪些模块导致漂移；
- 可与资产卡和镜头表对应；
- 支持批量生成和版本控制。

## 7.4 负面约束

负面约束应针对真实高风险问题，而不是无限堆词。

常见类别：

```text
无额外人物
无错误服装
无文本/水印/标志
无畸形手部
无多余肢体
无脸部漂移
无年龄变化
无肤色漂移
无道具消失
无错误左右方向
无不合理镜头运动
无未设计的突兀景别切换（不禁止已批准切点）
```

注意：

- 某些模型不支持负面提示词，或对其权重有限。
- 负面约束不能替代合格的参考图和关键帧。
- 如果一个错误重复出现，应改善输入资产、镜头拆分或生成策略，而不是只增加更多否定词。

## 7.5 修订前后的关键约束回归

以当前有效完整场景剧本为源，同时比较上一实际执行版与本版卡片、参考映射和 Prompt：
`必要信息或约束及来源 | 保留/修改/删除 | 具体画面、动作或对白承载位置 | 理由及下游复验`。
在现有 Revision/Coverage Map 内记录，不另建逐句台账。只跟踪影响人物选择、关系、因果、
关键空间、安全、权利及制作要求的内容，不把所有文字变化变成审批。
删去某句台词或某种行为后，检查它承担的判断依据、交流、后果是否仍被承载；镜头只写
“观察/核对/发现”而没有具体证据，不算完成转译。已有画面能清楚承载时允许删台词，
也允许有意沉默；不设对白字数、角色发言次数或镜数下限。后期旁白的安排不自动取消角色交流。
锁定约束消失、冲突或无依据降级时先处理，不能用新哈希、较长 Prompt 或“更严格”代替语义复验。
是否建立 Notice 及批准层级按控制合同 §7.2 和当前有效授权判断；旧约束也可能有错，应修权威源而非永久照抄。
保留旧版本和 RUN 的历史身份；当前变更建立对应新版本与必要的新验证，不覆盖旧 RUN 补造成片证据。

# 8. 生成策略选择

## 8.1 文生视频

适合：

- 氛围镜头
- 空镜
- 建立镜头
- 概念探索
- 非关键路人
- 不需要严格连续的人物剪影
- 视觉实验

风险：

- 人物外貌、服装和空间容易漂移；
- 很难精确控制道具、手部、文字和复杂动作；
- 适合探索，不适合直接承担关键叙事镜头。

## 8.2 图生视频

适合：

- 主要角色镜头
- 对话镜头
- 关键道具
- 特定构图
- 需要与前镜连续的镜头
- 需要保持场景布局的镜头

优先输入：

```text
已批准的角色/场景关键帧
+ 与批准路线对应的单镜头或原生多镜头提示
+ 明确的镜头运动
```

## 8.3 首尾帧控制

适合：

- 人物从站立到坐下；
- 手从拿着道具到放下道具；
- 人物从看向门口到看向手机；
- 角色从空间 A 移到空间 B 的局部运动；
- 情绪由压抑到决断的可见状态变化。

首帧和尾帧必须在以下方面一致：

- 角色身份
- 服装
- 地点
- 光线
- 道具
- 时间
- 角色朝向
- 空间结构

如果首尾帧本身不连续，视频模型无法可靠修复。

## 8.4 混合策略

真实生产中可混合：

| 内容 | 优先策略 |
|---|---|
| 主角特写 | 角色参考 + 图生视频 |
| 关键道具交接 | 关键帧 + 短动作生成 |
| 两人对话 | 正反打拆镜 + 反应镜头 |
| 城市外景 | 文生视频或背景生成 |
| 屏幕 UI | 后期合成，不依赖视频模型生成文字 |
| 手机短信 | 后期图层/动效 |
| 快速打斗 | 拆成局部动作 + 音效 + 剪辑 |
| 大型事故 | 闪光/声音/反应/后果镜头拼接 |
| 复杂群像 | 实拍、静帧、合成或减少叙事依赖 |

# 9. 动作、对白与声音

## 9.1 动作拆分

不要要求：

```text
人物跑进房间，推开门，看到尸体，尖叫，捡起手机，
给警察打电话，又被背后的人打晕。
```

拆为：

```text
镜头 1：人物冲到门前，手握门把。
镜头 2：门被推开，人物停住。
镜头 3：人物视角或局部展示关键发现。
镜头 4：人物特写，表情变化。
镜头 5：手抓住手机。
镜头 6：背后阴影进入画面。
```

剪辑、音效与反应镜头会让动作更可信，也更易控制。

## 9.2 对话镜头

对话生成建议：

- 一句或一小段台词对应一个镜头意图；
- 使用正反打、侧面双人镜头、手部/道具插入镜头、反应镜头；
- 口型若不可靠，考虑后期配音、局部遮挡、背影、侧脸或剪辑规避；
- 重要情绪信息不要只依赖嘴型，使用眼神、停顿、手部和空间距离。

先确定说话者此刻想从对方得到什么、正在隐瞒或担心什么、听到前一句后怎样改变，再调整口语。
分享、试探、歉意、安抚、惊喜可以有不同的语气词与句法；不为每句统一加感叹词，也不把配角写成
无条件赞同的答题器。情绪变化要落在可演的目光、声量、犹豫、动作或相互回应上，见 §7.2.1 的逐镜绑定。
角色对白、画外对白、旁白、画面说明、环境声与动作音效分开标识；有意的沉默同样可以承载交流。
原生双人戏可在同一 Segment 组织正反打或双人景，不强迫逐人独立生成；完整交流与可剪性按真实回片判断。

## 9.3 声音后置

除非工具在当前项目中已验证音画一致性，否则建议将：

- 配音
- 环境音
- 音效
- 音乐
- 手机/终端 UI 声
- 字幕
- 屏幕文字

视为后期层，而非交给视频模型一次生成。

原因：

- 声音后置更容易修改；
- 便于多语言版本；
- 可避免错误文字、错位口型、不可控噪音；
- 可通过声音弥补视觉无法低成本呈现的大事件。

---

## 9.4 系列声音身份与生成前分工

在现有声音清单中登记 `说话身份/声音参考或选定音色/适用段落/生成责任/预计声画点`。
旁白、角色对白、环境声与音乐分开：同一旁白跨段保持身份，不把“温暖声音”当作相同声线已被锁定的证据。
具体性别、语言、口音与原生/后期路线由项目选择，不设置所有作品通用的声音偏好。

若选择后期统一旁白，视频执行包须说明不生成旁白、不让角色复述旁白，保留动作与叙述所需时间；
按授权保留原生角色对白及可用环境声。不要先随机生成混合旁白，再假定后期能无损分离。
返回混音含多余人声时先评估可编辑性；需重配、补环境声或重生成时遵守当前委托，不掩盖代价。
声音参考的使用仍须具有相应权利，不能把选定声线理解为未经许可克隆真实人物。

环境声按地点、距离和主次组织，在对白下适当让位，跨同场切镜保持连续；地点变化时有相应声场变化。
岸边的风浪/鸟声、水下声场、局部动作声不是每镜全套必填。音乐需独立安排和授权，不用音量制造虚假节奏。
声音是否存在、说话人是否正确、声画点是否合适，依实际听审；文本、波形和 ASR 不单独证明听感一致。

# 10. 连续性系统

## 10.1 连续性日志

每完成一个批准镜头，更新：

```md
# Continuity Log

| 镜号 | 场次 | 剧情时间 | 角色位置 | 面向 | 服装状态 | 伤病 | 持有道具 | 道具位置 | 光线 | 情绪状态 | 进出方向 | 批准版本 | 风险 |
```

示例：

```md
| S03_SH012 | S03 | 夜 | 林夏在桌子左侧 | 面向右 | WORK_01 | 右手擦伤 | 停职通知（左手） | 玻璃桌上方 | 冷蓝主光/暖黄逆光 | 克制愤怒 | 镜头后向右转身 | v03 | 通知不可消失 |
```

## 10.2 连续性锚点

按本镜叙事需要选择连续性锚点，不用固定数量判定通过：

- 人物位置
- 人物朝向
- 服装状态
- 手持物
- 伤病/污损
- 光线方向
- 场景入口/出口
- 前镜结束姿势
- 后镜开始姿势
- 时间与天气

没有全场定位任务的特写不必展示建筑锚点；仍核对该镜头真正相关的身份、视线或接触关系。

## 10.3 连续性优先级

当模型输出“更好看”但不连续时，优先级如下：

```text
剧情事实
> 角色身份
> 关键道具/伤病/服装
> 空间与方向
> 情绪与表演
> 美学风格
> 偶发视觉奇观
```

不要为了一个漂亮镜头，牺牲观众对人物和故事的理解。

# 11. 质量控制

## 11.1 三层 QC

每个镜头至少执行三层审核：

先处理安全、权利、严重身份错误与不可播放技术错误等不可抵消硬门；硬门通过后，实际裁决顺序是
叙事可读性 → 可剪性与空间连续性 → 技术质量 → 风格微差。下列 A/B/C 是检查维度，不表示用技术瑕疵
优先级覆盖叙事判断。

### A. 技术 QC

- 分辨率、帧率、时长、编码是否正确？
- 是否存在闪烁、抖动、穿模、卡顿、跳帧？
- 是否存在多余肢体、错误手部、面部畸变？
- 是否有水印、错误文字、品牌标识或不应出现的人物？
- 画幅和安全区是否正确？

### B. 连续性 QC

- 是否为正确角色？
- 外貌、发型、服装、伤病、首饰是否一致？
- 道具是否正确且在正确手中？
- 空间布局、门窗、光线和方向是否一致？
- 人物进出方向和视线是否匹配？
- 与前后镜头的姿态和情绪能否剪接？

### C. 叙事 QC

- 观众一眼能否看懂本镜重点？
- 是否完成镜头表中的叙事功能？
- 动作是否支持台词或声音？
- 反应是否足够传递信息？
- 是否有无意义但抢注意力的视觉元素？
- 删除本镜会失去什么？若什么都不失去，考虑删除。

## 11.3 序列证据、可观察性与归因

完整序列另按导演参考 §7 审查观众理解、人物选择、切点与声画桥；单镜 QC 的总和不等于序列通过。
在现有审查报告中分别记录：

| 层次 | 最小证据 |
|---|---|
| 观察 | 实际输出版本、时间/画面区域、看见或听见的事实；未直接观看时注明材料来源 |
| 可观察性 | 对该属性能否判断、限制是什么；不可辨不等于缺失，也不等于通过 |
| 要求比较 | 当前锁定要求或允许的创作空间、是否满足、对观众的影响 |
| 归因 | 实际输入/Prompt/模型执行/后期/审查证据；区分事实与假设，可未知或多因 |
| 处置 | 最小修法、适用复验及所需权限；不因审查建议自动追加生成 |

编码、码率、采样率或标签变化只提示交付轮廓不同；无下载链证据时写来源待核，不能据此判非原件。
可辨的叙事、关系及细节继续审；确实不可辨的属性单项记明时间与限制，不把整片停审。
下一次下载只能证明该次来源，不能反推旧片下载路径。波形能量不能单独证明某句台词出现。
画面违约不自动等于模型根因：先核对真实上传图是否含冲突、Prompt 是否要求继承它、后期是否用错片；
输入明确而执行偏离可记“模型执行未满足该约束”，仍不预装未经验证的次因。
新发现和新标准以追加证据处理，不撤销旧用户接受事件，不重写历史 RUN。

## 11.4 将整集反馈沉淀为可复用方法

在已有复盘中记录“实际输入与输出身份 → 用户看到的结果 → 哪个决策值得保留/改变 → 适用条件 →
尚存问题与下次核验”，不另造分数证明。正面整集反馈是采用这套制作组合的实用证据，应如实记录，
但图数、表演、场景与 Prompt 同时变化时不能宣称某一因素单独致效，也不能推成模型天花板或普遍稳定率。
流程知识进入通用参考；具体角色、世界规则、声音选择、图片数量、用户原话和私有路径留在项目记录。
某段获接受与源文件存在、正式交付完成、Skill 激活是不同事实；不要用整集满意倒写旧 RUN 或关闭未处理门禁。

# 12. 对抗式制作审查

## 12.1 故事守门人

质疑：

- 是否在分镜或提示词中悄悄改掉了人物选择？
- 是否为了视觉奇观牺牲了剧情因果？
- 是否删去了让观众理解行动的必要镜头？
- 是否用炫技镜头替代了人物反应？
- 观众能否只靠画面和声音理解核心状态变化？

## 12.2 连续性检察官

质疑：

- 角色在上一镜的位置、朝向和服装是否正确延续？
- 伤病、污渍、首饰、发型、手机壳、道具是否漂移？
- 门窗、桌椅、屏幕、光线和时间是否变化？
- 镜头是否跨越了空间轴线？
- 角色是否无故多出或消失？
- 关键证据是否在镜头间改变内容或位置？

## 12.3 模型风险制片人

质疑：

- 是否让模型承担了复杂群像、精确手部交接、可读文字、长对白、连续打斗或复杂空间运动？
- 是否能通过拆镜、后期、静帧、声音或实拍降低风险？
- 是否将昂贵或不稳定镜头放在不可替代的叙事节点？
- 是否留有备选镜头或降级方案？
- 单镜头失败是否会阻塞整场制作？

## 12.4 法律与伦理守门人

质疑：

- 是否使用了无授权的真实人物肖像、声音、角色或品牌？
- 是否生成可能被误认为真实新闻、真实证据或真实人物陈述的内容？
- 是否涉及未成年人、裸体、性剥削、暴力美化、仇恨或自残风险？
- 是否使用了真实地点、机构、产品或制服并造成误导？
- 是否对 AI 生成、合成声音或虚构内容做了项目所需的透明标识？

本 Skill 不提供法律意见。涉及商业发布、真实人物、敏感内容、跨境发行或平台政策时，必须由权利方、法务和目标平台核验。

# 13. 失败模式与修复

下表是诊断候选，不是由症状直接断定根因；先按 §11.3 核对证据，再选择修复。

| 失败模式 | 待核验原因 | 候选修复 |
|---|---|---|
| 角色每镜换脸 | 无统一参考、提示词描述漂移 | 建角色卡、多角度参考、图生视频 |
| 服装持续变化 | 未定义服装状态 | 使用 wardrobe ID 和锁定参考 |
| 手和道具错误 | 一镜要求复杂交接 | 拆手部特写，改用关键帧或后期 |
| 场景像不同地点 | 参考矛盾、关键关系缺证、执行偏离或后期错配 | 核对实际输入与关键关系，再决定补参考、改覆盖或修后期 |
| 人物左右反复跳 | 未维护轴线 | 建立视线/轴线表，重做关键帧 |
| 口型不匹配 | 让模型承担长台词 | 后期配音、短句、侧脸或反应镜头 |
| 屏幕文字乱码 | 依赖模型生成 UI | 后期叠加可编辑 UI/字幕 |
| 长镜头失控 | 动作和变量过多 | 拆成多个短镜头 |
| 画面很美但看不懂 | 镜头无叙事功能 | 回到场景目标和镜头功能 |
| 后半集资产爆炸 | 剧本未考虑可制作性 | 合并地点、角色和道具，重写降级 |
| 生成成本失控 | 没有候选筛选和版本纪律 | 先关键帧、后视频；记录批次与成功模板 |
| 风格越做越混乱 | 没有风格圣经 | 锁定画幅、色板、材质、光线和构图规则 |

# 14. 人机协作边界

## 14.1 人必须决定的事

AI 可以生成候选画面，但人必须负责：

- 叙事优先级
- 角色与主题
- 镜头取舍
- 视觉一致性标准
- 是否真正完成情绪和信息传递
- 版权与伦理判断
- 预算分配
- 锁定版本
- 最终剪辑与声音节奏

## 14.2 AI 适合承担的事

AI 可以高效辅助：

- 概念探索
- 场景气氛候选
- 角色服装迭代
- 分镜变体
- 资产命名与表格初稿
- 提示词模块组合
- 批量生成候选
- 连续性异常初筛
- 字幕、翻译和多语言辅助
- 低风险 B-roll 与过场镜头

不要把“AI 能生成”误判为“AI 能自主完成导演、制片、剪辑、表演和版权清权”。

## 15.3 确定性导出包使用说明

本节说明如何使用导出包，不重新定义其机器格式。权威边界如下：

- `governance/control-schema.json` 的 `export_scope` 决定 selector、必需 Artifact 类型、
  上游引用闭包、路径映射、固定排除与路径安全规则；
- WP4b 提供的 exporter/verifier 实现决定实际 CLI、manifest 序列化、摘要字节与错误码；
- 本 reference 只解释工作流程。schema 与实现不一致时必须阻断并修复，不能由本文任选一方覆盖另一方。

使用者准备四项输入：源项目根、目标 baseline、scope selector 和输出目录。selector 取值为
`project / season / episode`；对应必需 Artifact 类型必须已经存在并属于目标 baseline。

最小流程：

```text
锁定目标 baseline
→ 选择 project / season / episode
→ 从源项目按 schema 独立推导 expected set
→ exporter 写入临时输出并生成 manifest 与摘要 sidecar
→ verifier 再从源项目独立推导 expected set
→ 比较 expected set == manifest set == actual output set
→ 验证逐文件摘要、包摘要、路径和引用闭包
→ 原子发布通过验证的导出目录
```

输出目录必须位于源项目 payload 树之外；源与输出任一方向嵌套都应拒绝。payload 路径使用
UTF-8 与 POSIX `/`，保持源项目相对路径，并拒绝绝对路径、`..`、symlink 或 junction 越界。
`manifest.sha256` 与包摘要 sidecar 是验证材料，不属于 payload 本身。

WP4b 已提供可执行 exporter/verifier。先查看 `--help`，再使用以下真实入口；不得手工复制后宣称 VERIFIED：

```powershell
python -X utf8 scripts/export_handoff.py <SOURCE> <OUTPUT> --baseline <BASELINE> --selector project --schema governance/control-schema.json
python -X utf8 scripts/verify_handoff.py <SOURCE> <OUTPUT> --baseline <BASELINE> --selector project --schema governance/control-schema.json
```

只有 verifier 返回 `PASS`，且 `expected set == manifest set == actual output set` 时，导出目录才可进入发布流程。
`season` 与 `episode` 当前是 schema 定义的类型范围配置，不含单季／单集 ID 过滤语义；不得把它们解释为
“自动选择某一集”。如需该能力，先通过 Notice 扩展 schema，再更新两条 CLI 与负向测试。

## 15.4 面向实际操作者的执行入口

生成包交付应能直接操作，而不要求用户记住目录结构。沿用项目约定的入口和命名；没有约定时，
准备一个 `START_HERE.md` 及逐段目录，在回复中直接提供入口和下表，而非只给裸路径或再套一层索引：

```md
| 段与任务 | 实际段文件夹 | 全部上传图（按顺序） | 完整 Prompt | raw 文件夹 | 建议输出原名 |
```

逐段链接到真实文件夹、每张实际图、完整文本和 raw；不要只写“见同上”。发出前检查链接存在、数量和顺序
与输入映射一致。聊天中的本地链接用当前宿主可点击的绝对路径，包内引用保持可搬运；不把个人绝对路径写进 Skill。
回片时先检查 raw，保留用户实际文件名与原字节；有文件就给直接链接，不以建议命名不同认定未交付。
明确哪些文件已存在、哪些已审阅、哪些获生成授权。整集阶段优先给已核实的完整视频与工程入口，
原始逐段输入仍可追溯；入口便利性不授予生成、重试、重命名或发布权限。
这属于操作指引，不替代 §15.3 导出格式或其 verifier。
