# Expected Deliverables and Acceptance Tests

> 本文件是 `governance/control-plane-contract.md` 的验收投影。
> 状态、ID、Review Decision 和 Test Result 以控制契约为准。

> 文件路径：
>
> ```text
> ~/.codex/skills/professional-screenwriter/tests/expected-deliverables.md
> ```
>
> 本文件定义 Professional Screenwriter Skill 的：
>
> ```text
> - 最小可交付产物；
> - 每项产物的可观察验收标准；
> - 必须失败的反例；
> - 可追溯关系；
> - 阶段门禁；
> - 长片与竖屏微短剧的端到端测试要求；
> - 对抗式审查与发布前验证要求。
> ```
>
> 本文件不用于：
>
> ```text
> - 替代 Story Bible；
> - 替代项目实际的交付清单；
> - 替代客户、制片、平台、合同或法务要求；
> - 通过“文件存在”伪造项目完成；
> - 把审美偏好伪装成不可验证的验收条件。
> ```

---

# 0. 测试目的

## 0.1 唯一问题

```text
当本 Skill 接到一个明确项目任务时，

它是否能稳定地产出：
可读、可写、可审、可追溯、可同步、可交接的创作文件，

并且在上游事实、格式、权利或生产约束变化时，
不会让下游文件静默失效？
```

## 0.2 什么叫“通过”

```text
通过
≠
生成了很多 Markdown 文件。

通过
=
每个必要交付物存在；
每个交付物有明确职责；
关键事实可以追溯；
跨文件不存在未解释的 P0 矛盾；
上游变化能够找到、同步、验证并留痕；
项目能从开发进入剧本、生产与交接。
```

## 0.3 什么叫“失败”

以下任一情况均视为失败：

```text
- 只生成剧本，没有项目约束、Bible、结构或连续性依据；
- Story Bible、大纲、场景卡与剧本存在关键事实冲突；
- 人物在不知情时按作者知道的信息行动；
- 结构节点只有名称，没有因果、选择与后果；
- 竖屏短剧有“钩子”但没有兑现计划；
- 付费点在兑现前只延迟信息或强行断章；
- 生产包使用了与当前剧本不兼容的版本；
- 外部事实、第三方素材或 AI 输入/输出没有记录必要限制；
- 上游变更后只改一处剧本，其他下游文件静默过期；
- 文件写着“已审查”却没有检查范围、发现、结论、负责人或版本；
- 文件写着“最终版”却无法回答它相对哪个基线最终。
```

# 2. 通用 Definition of Done

> 所有交付物只有同时满足“存在、可读、可用、可追溯、可审查、
> 与基线一致”时，才能标记为 `DONE`。
>
> “完成”的定义必须可检查，不依赖“感觉差不多”。

## 2.1 通用完成门槛

每个交付物必须：

- [ ] 有明确文件名、路径、版本、日期、状态和负责人
- [ ] 有单一职责，不与其他权威文件重复争夺事实主导权
- [ ] 说明输入、输出、适用范围与不适用范围
- [ ] 使用当前 `project-manifest.md` 声明的项目 ID、格式、语言、画幅、时长和阶段
- [ ] 指向或可定位其上游事实源、结构源、来源、权利或生产依赖
- [ ] 与当前有效 Story Bible、大纲、场景卡、剧本或生产包不存在 P0 冲突
- [ ] 对关键假设、未知项和待决项使用明确状态，不将其伪装为既成事实
- [ ] 有可执行的验收标准，而非“更精彩”“更高级”“更像电影”等模糊描述
- [ ] 经适用的对抗式审查，P0 已关闭或项目处于明确 `BLOCKED`
- [ ] 若取代旧文件，旧文件已标记 `SUPERSEDED`、`ARCHIVED` 或 `DO_NOT_USE`
- [ ] 若修改上游事实，已评估是否需要 `upstream notice`
- [ ] 若使用第三方材料、事实、AI、真实人物或品牌，已建立相应来源/权利记录
- [ ] 被批准时，记录批准人、批准版本、批准时间与批准范围
- [ ] 能在不依赖作者记忆的情况下被第三方理解和继续使用

## 2.2 不可接受的“完成”表述

以下表述不能作为验收结论：

```text
- “已经写完了”
- “故事很完整”
- “感觉不错”
- “应该没有问题”
- “AI 能做出来”
- “观众应该会喜欢”
- “客户大概同意”
- “文件都在”
- “最后再改”
- “先拍再说”
```

应改为：

```text
- “SCRIPT v1.2.0 已通过连续性、因果与生产审查；
   无未关闭 P0；当前锁定范围为第 1–24 场；
   批准人：[角色]；日期：[YYYY-MM-DD]。”

- “第 8 集付费点前的核心承诺为 [X]；
   第 9 集前 20 秒兑现 [Y]；
   证据位置：[文件/段落]；
   审查状态：PASS。”
```

# 3. 追溯模型

## 3.1 必须存在的追溯链

```text
项目目标与约束
→ 项目清单
→ 故事事实与研究边界
→ Story Bible
→ 因果结构与格式策略
→ 大纲/分集地图
→ 场景目标与状态变化
→ 场景卡
→ 屏幕可见表达
→ 剧本主源
→ 审查与修订
→ 生产资产、镜头、声音、字幕、UI
→ 制作交接与发布包
```

## 3.2 追溯 ID 规则

| ID 前缀 | 对象 | 示例 |
|---|---|---|
| `PROJECT-` | 项目 | `PROJECT-TIDELINE-001` |
| `CON-` | 不可协商约束 | `CON-003` |
| `ASM-` | 关键假设 | `ASM-004` |
| `CLM-` | 外部事实主张 | `CLM-007` |
| `SRC-` | 来源 | `SRC-012` |
| `RGT-` | 权利项 | `RGT-005` |
| `TP-` | 第三方材料 | `TP-009` |
| `BIBLE-` | Bible 事实 | `BIBLE-CHAR-003` |
| `ARC-` | 人物弧 | `ARC-PROTAG-001` |
| `BEAT-` | 结构节点 | `BEAT-05` |
| `EP-` | 集 | `EP-08` |
| `SC-` | 场景卡 | `SC-024` |
| `SCRIPT-` | 剧本版本 | `SCRIPT-v1.2.0` |
| `ASSET-` | 生产资产 | `ASSET-PROP-014` |
| `SHOT-` | 镜头 | `SHOT-1-024B` |
| `AUDIO-` | 音频/配音 | `AUDIO-VO-011` |
| `SUB-` | 字幕/UI/屏幕文字 | `SUB-EP08-027` |
| `NOTICE-` | 上游变更通知 | `NOTICE-018` |
| `REVIEW-` | 审查报告 | `REVIEW-006` |
| `MIG-` | 迁移任务 | `MIG-003` |
| `LOCK-` | 锁定点 | `LOCK-SCRIPT-001` |
| `DEL-` | 交付物 | `DEL-010` |

> ID 的目的不是制造官僚层级。
>
> 它的目的在于：当一个人物事实、场景、镜头、资产、来源或权利状态改变时，
> 团队可以准确找出依赖对象，而不靠全文搜索或个人记忆。

## 3.3 最小追溯测试

对任意一个关键元素，必须能双向回答：

```text
向上追溯：
这个剧本/场景/镜头/资产为什么存在？
它服务哪个项目目标、故事事实、结构节点或生产约束？

向下追溯：
这个项目目标、事实、规则、付费点、权利限制或生产约束
会影响哪些大纲、场景、剧本、镜头、资产、字幕和交付物？
```

若无法双向追溯，则测试失败。

# 5. DEL-001：项目 Manifest

## 最小内容

- [ ] 项目名称、ID、当前版本、状态、阶段和健康状态
- [ ] 项目目的、一句话定义、成功标准与不可接受失败结果
- [ ] 格式、类型、受众、市场、语言、画幅、时长、平台和商业模式
- [ ] 明确范围、非目标、不可协商约束、可协商变量和关键假设
- [ ] 当前有效 Story Bible、大纲、场景卡、剧本、审查、来源、权利和生产文件路径
- [ ] 当前锁定点、变更门槛、审批权、负责人、风险、阻断项和下一门禁
- [ ] 当前版本之间的兼容性结论
- [ ] 下一步任务及其完成定义

## 验收测试

| Test ID | 测试 | 通过条件 | 失败条件 |
|---|---|---|---|
| MAN-001 | 身份完整性 | 项目 ID、版本、阶段、负责人可定位 | 只能从聊天或目录名猜测项目身份 |
| MAN-002 | 范围边界 | 有明确非目标与不可协商约束 | “做高质量内容”等空泛表述 |
| MAN-003 | 基线一致性 | 所有权威文件路径、版本、状态可定位 | 多个文件都自称最新版 |
| MAN-004 | 决策权 | 每类关键决定有最终批准人 | 团队不知道谁能锁剧本/批准变更 |
| MAN-005 | 可恢复性 | 新成员只读 Manifest 可知道下一步 | 工作依赖作者个人记忆 |
| MAN-006 | 阶段门禁 | 当前阶段的允许、禁止、退出条件明确 | 未锁剧本已被当作生产基线 |

## 必须失败的反例

```text
项目 Manifest 写：
“这是一个很感人的悬疑短剧，适合年轻人。”

但没有：
- 平台；
- 集数；
- 单集时长；
- 画幅；
- 商业模式；
- 目标市场；
- 当前 Bible；
- 当前剧本；
- 锁定状态；
- 负责人；
- 下一门禁。

结果：FAIL。
```

# 6. DEL-002：来源与研究日志

> 仅当项目使用外部事实、专业知识、历史、医疗、法律、工程、
> 地理、行业、现实机构、新闻或其他需要核验的材料时必需。

## 最小内容

- [ ] 每个关键外部主张有 `CLM ID`
- [ ] 每个来源有 `SRC ID`、URL/出处、获取日期、来源类型与可信度判断
- [ ] 区分事实、推论、创作选择与未验证假设
- [ ] 记录来源支持什么、不支持什么、适用范围与失效条件
- [ ] 高风险主张有复核日期、负责人和必要的专业顾问状态
- [ ] 若来源内容被作为素材使用，已关联 `TP ID` 和权利处理

## 验收测试

| Test ID | 测试 | 通过条件 | 失败条件 |
|---|---|---|---|
| SRC-001 | 主张可追溯 | 任一关键事实可找到支持来源 | “网上说的”“模型知道” |
| SRC-002 | 表达/事实分离 | 事实来源不自动被标记为可复用素材 | 把新闻图片当作免费剧照 |
| SRC-003 | 限制可见 | 记录来源不确定性、地域、时间和方法限制 | 单一来源被写成绝对真理 |
| SRC-004 | 高风险升级 | 医疗、法律、安全等有顾问/复核路径 | 用虚构需求规避必要核验 |
| SRC-005 | 变更传播 | 来源推翻关键事实后创建 Notice | 只更新研究笔记，剧本仍写旧事实 |

## 最小内容

- [ ] 每项进入项目的第三方材料有 `TP ID`
- [ ] 每项实际资产有 `ASSET ID`

- [ ] 未清权、过期、争议或禁止材料不会进入最终交付

| RGT-006 | 发布阻断 | P0/争议/过期项阻止发布 | 未授权素材仍进入成片 |

# 8. DEL-004：Story Bible

## 最小内容

Story Bible 必须包含并区分：

- [ ] Logline、核心问题、主题命题与对立命题
- [ ] 项目类型、调性、受众、格式边界和内容边界
- [ ] 主角的外部目标、内部需求、错误信念、资源、限制、失败代价与高潮选择
- [ ] 主要对抗力量的目标、资源、策略、限制、盲点与主题功能
- [ ] 关键人物的欲望、恐惧、秘密、知识状态、关系与弧线
- [ ] 世界规则、成本、例外、限制与不可轻易解决的问题
- [ ] 时间线、地点、道具、伤病、服装、关系与身份的连续性信息
- [ ] 信息矩阵：谁在何时知道、相信、误解或隐藏什么
- [ ] 未确定项、研究项、风险项和来源引用
- [ ] 当前版本、状态、负责人、最后审查日期与权威性声明

## 验收测试

| Test ID | 测试 | 通过条件 | 失败条件 |
|---|---|---|---|
| BIB-001 | 主角发动机 | 目标、限制、代价、错误策略和选择可见 | 只有性格形容词 |
| BIB-002 | 对抗主动性 | 对手能主动采取策略并造成后果 | 对手只在需要时出现 |

# 26. 评分规则

## 26.1 单项状态

| 状态 | 含义 |
|---|---|
| PASS | 所有必要验收条件满足，无未关闭 P0/P1 |
| CONDITIONAL PASS | 无 P0；存在有负责人、补偿、截止日期的 P1/P2 |
| BLOCKED | 缺少关键输入、审批、权利、研究、基线或生产决策，不能安全继续 |
| FAIL | 存在关键矛盾、无法追溯、未处理 P0、错误锁定或不满足核心输出 |
| NOT_APPLICABLE | 对当前项目形式确实不适用，且已说明理由 |

## 26.2 严重等级

| 等级 | 定义 | 对阶段的影响 |
|---|---|---|
| P0 | 会使故事核心、事实、权利、安全、生产或发布无效/高危 | 阻止 LOCKED、PRODUCTION、RELEASE |
| P1 | 明显损害一致性、质量、成本、可信度或交付，但可在门禁前修复 | 阻止正式交付，除非书面接受 |
| P2 | 可改进、局部不一致、可控优化 | 不必阻止阶段，但应排入修订 |
| INFO | 记录性发现或未来建议 | 不影响通过状态 |

## 26.3 端到端通过门槛

| 测试 | 最低通过条件 |
|---|---|
| E2E-FEATURE | 所有必需交付物存在；无 P0；至少 90% 核心断言通过；变更传播完整 |
| E2E-VERTICAL | 所有必需交付物存在；无 P0；钩子/兑现/付费断言全部通过；9:16 可读性通过 |
| E2E-REWRITE | 场景目标、对抗、转折、知识与连续性断言全部通过 |
| E2E-CHANGE | 影响文件 100% 被枚举；关键下游 100% 同步或明确 BLOCKED |
| E2E-RIGHTS | P0 权利项被阻断/替换；来源与素材边界无混淆 |
| E2E-HANDOFF | 交接版本一致；关键镜头/资产/声音可追溯；无未记录生产 P0 |
| E2E-ADVERSARIAL | 识别至少 80% 预埋 P0/P1；无明显 P0 漏检 |

# 29. 对抗式最终审查

在宣布本 Skill “架构完成”或某个项目“可交付”之前，必须逐项回答。

## 文件存在性检察官

- 这些文件是真的承担职责，还是只是空模板？
- 有没有文件名看似专业，却没有当前版本、负责人、状态和实际内容？
- 是否有两个文件重复维护同一事实，且没有权威优先级？
- 是否有关键控制点只存在于聊天记录或某个人脑中？
- 删除任何一个文件后，团队是否知道它承担什么职责？

## 因果检察官

- 大纲是否由人物选择与对手反制推动？
- 中点是否真正改变问题而不是提高音量？
- 高潮是否需要主角支付新代价？
- 结局是否兑现入口承诺、核心问题和主题命题？
- 是否有“因为作者想要”而非“因为前面导致”的关键转折？

## 信息检察官

- 每个关键秘密的知情者、误解者、传播路径和揭示时点是否可追溯？
- 是否有角色读取了作者笔记、提前知道消息或忘记已知事实？
- 是否有被删除的线索仍在后续被回收？
- 是否有钩子没有兑现、兑现太晚或以假揭示代替兑现？

## 连续性检察官

- 人在哪里、何时、带着什么、伤在哪里、穿什么、知道什么？
- 道具、证据、手机、钥匙、钱、文件、武器或衣物是否可以追踪？
- 路程、恢复、天气、时间、通讯和地点切换是否可能？
- 资产、剧本、镜头、字幕和声音是否来自同一事实基线？

## 生产检察官

- 每个关键创作承诺是否在当前预算、技术、画幅、人员、地点和排期内可实现？
- 竖屏是否真的按移动端可读性设计？
- AI 是否有角色一致性、口型、手部、文字、商标、声音与相似性控制？
- 实拍是否有地点、动作、演员、许可、安全、保险和后期策略？
- 是否存在已做资产反向绑架故事的情况？

## 权利检察官

- 哪些材料是事实，哪些是受保护表达？
- 所有外部素材、音乐、字体、图片、视频、地图、UI、代码、模型、声音和数据是否有可追溯状态？
- 是否误把“免费”“公版”“开放许可”“已购买”“AI 生成”当作无条件通行证？
- 是否存在未处理的真实人物、品牌、商标、肖像、隐私、合同或平台风险？
- 若明天收到权利异议，能否立刻定位、替换和回滚？

## 治理检察官

- 当前 Manifest 是否真的指向唯一有效基线？
- Change Log 是否说明当前版本与上一版的真实差异？
- 每项 L2-L4 变更是否有 Notice、同步任务和复验证据？
- `LICENSES/` 是否只放许可与权利材料，而非故事与研究文件？
- 是否存在未关闭 P0 却被标为 `LOCKED`、`READY` 或 `DELIVERED` 的文件？

# 30. 最终原则

```text
交付物不是“生成的文件”。

交付物是能够让下一位作者、制片、剪辑师、AI 操作员、
客户、审查者或法务人员在不依赖原作者记忆的前提下：

理解项目；
找到当前事实；
验证故事因果；
追踪人物、信息和连续性；
识别版本与变更；
判断权利与风险；
继续生产；
并安全交付的工作产品。

如果一个文件不能被验收，
它就不能被称为完成。

如果一个变化不能被追溯，
它就不是被管理的变化。

如果一个项目只能靠“作者记得”，
它就还不是可协作、可生产、可维护的项目。
```
